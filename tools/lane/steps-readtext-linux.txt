# READING WHAT A CONTROL SAYS -- roadmap item 28, on Linux.
#
# Every assertion in this directory used to be a PICTURE on this machine. Windows
# sends WM_GETTEXT and reads a pane's whole transcript back word for word; here,
# keys went in through XTest and frames came out through xwd, so the Linux half
# of the REPL case checked the PROCESS TABLE while the Windows half checked the
# conversation -- a weaker question, asked because the right one could not be.
#
# THIS CASE IS THE FIRST HERE THAT CAN FAIL WITHOUT A PERSON LOOKING. `text`
# counts its misses and the script exits non-zero, so it can be run FROM another
# script rather than watched. Run it as:
#
#   bash tools/lane/lane-linux.sh tools/lane/readtext.bas \
#        tools/lane/steps-readtext-linux.txt
#
# THE FIXTURE IS NEVER EDITED, deliberately. F9 saves before it runs, so a case
# that typed into the buffer would rewrite a checked-in file on every pass --
# which is the trap roadmap item 24 paid for.
raise
wait 800

# THE WINDOW DESCRIBES ITSELF before anything happens: the eight output tabs, by
# name, read out of the program rather than off a photograph of it.
text Watches
text Call Stack
text Variables
text Problems
shot 470-before-the-run

# RUN IT. F9 hands the fixture to the host and the Output tab fills.
#
# `key F9`, NOT `key {F9}`. The two drivers share six verbs of eight and NO KEY
# NAMES: Windows takes SendKeys braces, this side takes X keysyms. Writing the
# Windows spelling here cost a run on 2026-09-17 -- xdrive said "no keysym called
# {F9}", nothing ran, and the two text assertions below failed, which is the
# first time this directory has had an assertion that could say so.
key F9
wait 4000
shot 471-after-the-run

# AND THE ASSERTIONS THAT ARE NOT PICTURES. Both strings are the program's own
# output, so finding them proves three things at once: the run happened, the
# output reached the pane, and this script is reading the pane and not a cached
# copy of something else.
text lane-readtext-ok
text total=42
say Output
